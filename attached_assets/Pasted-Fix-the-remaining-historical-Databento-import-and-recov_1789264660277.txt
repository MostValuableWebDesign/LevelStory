1. Fix resume progress and checkpoint counter double-counting

Relevant files:

- `artifacts/api-server/src/lib/futures/multi-contract-replay.ts`
- `artifacts/api-server/src/lib/futures/historical-index-store.ts`
- `artifacts/api-server/src/lib/futures/historical-import-job-store.ts`

Current problem:

When an incomplete file is resumed, its saved partial counters are assigned to:

- `fileBaseRows`
- `fileBaseAcceptedRows`
- `fileBaseRejectedRows`

The importer then reparses that same physical file from the beginning and adds the new parser counters to those saved partial counters.

Example:

- Import is cancelled after 100,000 rows.
- Resume reparses the one-million-row file from its beginning.
- The job can report 1,100,000 rows instead of 1,000,000.

Required behavior:

- Separate totals from fully completed physical files from progress inside the current incomplete physical file.
- A resumed file that must be reparsed from the beginning must not add its previously parsed partial count to the new full-file parser count.
- Track:
  - `completedFileRows`
  - `completedFileAcceptedRows`
  - `completedFileRejectedRows`
  - current-file parser rows
  - current-file accepted rows
  - current-file rejected rows
- Calculate displayed cumulative progress as:

  `completed-file totals + current parser position`

- Do not use:

  `previous partial current-file total + reparsed current-file total`

- When the physical file completes, move its final counters into completed-file totals exactly once.
- Repeated resume operations must not increase totals unless new source rows are actually completed.
- Counters must remain monotonic and must never exceed the actual source totals.
- Final job counters must match the final import summary.
- Keep partition skipping independent from progress counters. Previously completed partitions may be skipped during SQLite writes even though the source stream is being reparsed.

Preserve the corrected batch ordering:

1. Snapshot partitions completed before the current batch.
2. Filter only against that snapshot.
3. Write current-batch one-minute candles.
4. Flush completed five-minute aggregation state.
5. Mark fully written dates complete.
6. Persist the checkpoint.

Do not reintroduce the earlier cross-date candle-loss bug.

2. Fully eliminate the cancel/resume worker race

Relevant files:

- `artifacts/api-server/src/routes/historical-data-upload.ts`
- `artifacts/api-server/src/lib/futures/historical-import-job-store.ts`
- `artifacts/levelstory/src/pages/backtest.tsx`

Required state flow:

`running → cancelling → cancelled_resumable → queued → running`

Current remaining race:

The active worker can set the job to `cancelled_resumable` before its `finally` block removes the job ID from `runningJobs`.

During that window:

1. The frontend sees `cancelled_resumable`.
2. The user presses Resume.
3. The route changes the job to `queued`.
4. `runImportJob()` returns because the previous worker is still in `runningJobs`.
5. The previous worker exits and removes itself.
6. The job can remain queued without an active worker.

Required behavior:

- Do not expose `cancelled_resumable` until all of the following are true:
  - the parser has stopped;
  - any incomplete transaction has been rolled back;
  - the last safe checkpoint is persisted;
  - the staging SQLite database is closed and preserved;
  - the old controller is removed;
  - the job ID is removed from `runningJobs`.
- Only after worker cleanup should the durable job state become `cancelled_resumable`.
- Alternatively, make Resume atomically wait for or claim execution after the previous worker releases ownership.
- A successful Resume response must guarantee that:
  - the job has an active worker; or
  - a durable queue mechanism will start it.
- Never return a successful queued Resume response when no worker was actually started.
- Prevent two workers from processing the same import.
- Resume during `cancelling` must return HTTP 409 with:
  “Cancellation is still in progress; wait for the importer to stop before resuming.”
- The frontend must continue polling while the state is `cancelling`.
- Show the Resume button only after `cancelled_resumable` is safely established.

Use atomic job-state transitions and worker ownership checks rather than timing assumptions.

3. Handle cancellation before a staging checkpoint exists

Current problem:

A job can be cancelled during upload materialization or validation before the staging SQLite database is created. It can then be labeled `cancelled_resumable`, but Resume rejects it because `stagingIndexPath` is null.

Required behavior:

Support two safe recovery modes:

A. Checkpoint resume

Use when a valid staging SQLite database and matching checkpoint exist.

- Verify the staging path exists.
- Verify the checkpoint is readable.
- Verify its source fingerprint matches.
- Resume using the saved completed partitions.

B. Safe restart

Use when cancellation happened before a staging checkpoint was created.

- Reuse already persisted uploaded/materialized source files when their size and fingerprint still match.
- Restart indexing from the beginning.
- Do not require `stagingIndexPath`.
- Do not require the user to upload the five-year file again.
- Preserve the previous committed historical library.
- Clearly label the action as “Restart import” if no checkpointed index work can be resumed.

Do not call a job checkpoint-resumable if it has no checkpoint. Represent the distinction explicitly, for example:

- `cancelled_restartable`
- `cancelled_resumable`

The frontend should display:

- “Resume import” for a valid staging checkpoint.
- “Restart import” when only the persistent source upload can be reused.
