1. Fix the critical cross-date batch data-loss bug

Primary file:

`artifacts/api-server/src/lib/futures/multi-contract-replay.ts`

Current defective sequence inside the `importHistoricalCsvBatch(...).onBatch` callback:

1. Iterate through every candle in the incoming batch.
2. Detect trading-date transitions.
3. Add previous dates to `completedPartitions`.
4. Filter the same batch using `completedPartitions`.
5. Write only the candles that remain.

Because a 10,000-row batch can contain several trading dates, dates detected as completed can be filtered out before their candles are written to SQLite.

Required processing order:

1. At callback entry, take an immutable snapshot of partitions that were already completed before this batch:
   `previouslyCompletedPartitions`.
2. Filter only against that preexisting snapshot.
3. Never filter current-batch candles using partition markers created while processing the current batch.
4. Write all non-previously-completed one-minute candles from the batch.
5. Incrementally aggregate and write their five-minute candles.
6. Detect which trading dates became fully closed by encountering a later date.
7. Flush all remaining five-minute state belonging to each closed date.
8. Commit the corresponding one-minute and five-minute SQLite writes.
9. Only after successful writes and aggregation, add:
   - `<contract>:1:<trading-date>`
   - `<contract>:5:<trading-date>`
   to `completedPartitions`.
10. Persist the checkpoint only after those partition writes are committed.

Do not mark a trading date complete merely because a later date was encountered before the current batch has been written.

Handle batch boundaries correctly:

- One trading date may span two or more parser batches.
- One parser batch may contain multiple trading dates.
- A five-minute bucket may span the boundary between parser batches.
- The final date for a contract must not be marked complete until the end-of-file buffer has been flushed successfully.
- Interleaved contract symbols must maintain independent date and aggregation state.
- Resuming must skip only partitions that were verified complete before the interrupted run.

Do not solve this by retaining the complete file in memory or changing `retainCandles: false`.

3. Eliminate the cancel/resume race condition

Relevant files:

- `artifacts/api-server/src/routes/historical-data-upload.ts`
- `artifacts/api-server/src/lib/futures/historical-import-job-store.ts`
- `artifacts/levelstory/src/pages/backtest.tsx`

Current problem:

The cancel route immediately changes the job to `cancelled_resumable` and exposes Resume while the previous importer may still be running. Pressing Resume immediately can encounter the existing `runningJobs` entry and fail to launch a replacement run. The old aborted run can then alter the resumed job’s state.

Required state flow:

`running → cancelling → cancelled_resumable → queued → running`

Cancellation requirements:

- The cancel route sets the state to `cancelling`.
- Abort the active controller.
- Do not expose or enable Resume while state is `cancelling`.
- The active importer must:
  - stop at the next safe boundary;
  - roll back any incomplete transaction;
  - write or retain the last verified checkpoint;
  - call `preserveAtomic()` or equivalent;
  - close the staging database;
  - remove itself from `runningJobs`;
  - then atomically change the job to `cancelled_resumable`.
- Only then should the Resume button become available.
- The cancel endpoint must not claim that a resumable checkpoint exists before preservation is confirmed.

Resume requirements:

- Resume only from `cancelled_resumable` or a verified recoverable `paused` state.
- Verify that `stagingIndexPath` exists and contains a compatible readable checkpoint.
- Verify the source fingerprint.
- Atomically claim the job so only one importer can resume it.
- Do not allow duplicate workers for the same job.
- If the previous worker is still stopping, return `409` with a clear “cancellation still in progress” message.
- The UI should continue polling during `cancelling`.
- Resume must continue from the retained staging index and preserve the previous committed library until successful replacement.

Normalize cancellation detection. Do not depend on an exact comparison with only:

`Historical import was cancelled.`

Handle cancellation errors generated by both the CSV importer and index builder, preferably with a typed cancellation error rather than string matching.

4. Stop silently truncating backtest selections to 10 sessions

Primary file:

`artifacts/levelstory/src/pages/backtest.tsx`

Current behavior:

`availableBatchDates` ends with:

`.slice(-MAX_BACKTEST_SESSIONS)`

This silently changes a range containing more than 10 stored dates into its final 10 dates. The user is not told that the requested period was changed, and the server never receives the excessive range.

Required behavior:

- Remove the silent `.slice(-MAX_BACKTEST_SESSIONS)`.
- Resolve all distinct stored dates inside the selected calendar range.
- Display the resolved stored-session count.
- If the count is 0, show a no-data message.
- If the count is 1 where the operation requires at least 2, show the existing minimum-session validation.
- If the count exceeds 10:
  - disable submission;
  - show a clear message such as:
    “This range contains 11 stored trading sessions. Select a range containing no more than 10.”
  - do not silently select the latest 10.
- Send the exact user-selected stored dates to the server.
- Keep the server-side limit authoritative in case a client bypasses the UI.

Update any remaining text that says “eligible scheduled dates” when it is actually counting stored dates.
