Objective

Correct the causal boundary between the prior and new ORB epochs, and prevent future positions from being reported as active during earlier ORB transitions.

1. Keep the reversal-confirming candle in the prior epoch

The current implementation ends the prior epoch with:

`candle.openTime < transition.confirmingCandle.openTime`

This removes the reversal-confirming candle at its open even though the new ORB direction is not effective until that candle completes.

Correct behavior:

- The previous ORB direction remains authoritative throughout the reversal-confirming candle.
- The reversal is confirmed only when that completed candle closes beyond the opposite ORB boundary and confirmation buffer.
- The new direction becomes effective at `transition.effectiveFromTimestamp`.
- The first candle evaluated under the new direction is the immediately following candle.
- Prior-epoch pullback, patience, and trigger evaluation must include the reversal-confirming candle.
- Do not allow the new epoch to use the confirming candle as its first pullback, patience, or entry candle.
- Do not retroactively invalidate a prior-direction candidate whose entry threshold was reached before the reversal became effective.

Use timestamps rather than the confirming candle’s open time when partitioning epochs.

The prior epoch’s visible window should extend through the confirming candle, subject to deterministic event ordering at its close. The new epoch window should begin at `effectiveFromTimestamp`.

2. Define same-timestamp event ordering

Create one explicit policy for events occurring on the reversal-confirming candle.

Recommended order:

1. Process intrabar stop and target events for any already-active position.
2. Process a previously armed prior-direction entry threshold if the available OHLC ordering proves it occurred before invalidation.
3. If entry-versus-reversal ordering cannot be proven from five-minute OHLC, mark the occurrence ambiguous instead of automatically expiring or confirming it.
4. Complete the candle.
5. Confirm the ORB reversal from the completed close.
6. Expire remaining pending prior-epoch arms and candidates.
7. Make the new ORB direction effective for the following candle.

Apply the project’s existing tick or one-minute disambiguation sources when available.

Do not:

- Let the new trend affect the confirming candle.
- Automatically discard a prior-direction trigger that occurred during the confirming candle.
- Use future candles to resolve the ordering.
- Permit both confirmed entry and expired-candidate disposition for the same occurrence.

3. Correct prior-epoch expiration after event ordering

At `effectiveFromTimestamp`:

- Include the real prior Phase 4 arm in `expiredArmIds` if it remained pending after processing the confirming candle.
- Include pending, unconfirmed prior-epoch occurrences in `expiredCandidateIds`.
- Do not expire an occurrence that became a confirmed entry before the reversal took effect.
- Do not expire an occurrence already terminated for an earlier independent reason.
- Record ambiguous same-candle cases explicitly.
- Continue managing an active position without reversing or closing it merely because the ORB trend changed.
- Keep `ORB_TREND_REVERSED` as the canonical reason for state that genuinely expires at the transition.

4. Fix the active-position interval predicate

`activeAccountPositionAt()` currently checks only whether the position exits after the queried timestamp. It does not ensure that the position had entered by then.

Use this interval:

`positionEntryTime <= queryTime < fullExitEffectiveTime`

For open positions:

`positionEntryTime <= queryTime`

Requirements:

- A position with an entry later than the queried transition must return false.
- A position entered exactly at the query timestamp follows the project’s documented same-timestamp ordering.
- A position fully exited exactly at the query timestamp must return false if exits are effective at that timestamp.
- An open position remains active after entry.
- Invalid position entry timestamps must not silently make a future position block earlier history. Return a conservative, explicitly audited result or reject invalid position evidence before reconciliation.
- Rename the predicate’s `entryTime` argument to `queryTime` or `evaluationTime` to avoid confusing it with `position.entryTime`.
