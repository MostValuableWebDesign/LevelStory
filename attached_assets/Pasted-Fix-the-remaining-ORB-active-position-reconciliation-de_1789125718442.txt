1. Correct the active-position interval

Current defect:

`activeAccountPositionAt()` returns true immediately when `fullExitTime` is null or invalid. That happens before checking whether `position.entryTime` is later than the query timestamp.

As a result, a future open or unresolved position can incorrectly block an earlier ORB transition.

Apply this order:

1. Parse and validate `position.entryTime`.
2. Parse and validate the query/evaluation timestamp.
3. If `positionEntryTimestamp > queryTimestamp`, return false.
4. If the position has no authoritative full-exit timestamp, return true.
5. If a valid full-exit timestamp exists, return:
   `positionEntryTimestamp <= queryTimestamp && queryTimestamp < fullExitTimestamp`

Equivalent rule:

For a closed position:

`entryTime <= queryTime < fullExitTime`

For an open or unresolved position:

`entryTime <= queryTime`

2. Exact timestamp behavior

Preserve the established ordering:

- Entry exactly at the query timestamp means the position is active.
- Full exit exactly at the query timestamp means the position is no longer active.
- Entry after the query timestamp means the position is not active.
- Partial exit does not release the gate while quantity remains open.
- A runner remaining open keeps the position active.
- A blocked or rejected candidate never becomes an active position.
- Contract-boundary resets remain unchanged.

3. Invalid timestamp handling

- Invalid position entry timestamps must continue producing `InvalidAccountPositionEvidenceError`.
- Invalid query timestamps must continue producing `InvalidAccountPositionEvidenceError`.
- A missing or invalid full-exit timestamp may be treated conservatively as an unresolved/open position, but only after verifying that its entry occurred on or before the query timestamp.
- Do not let conservative exit handling override the entry-time boundary.

4. ORB transition reconciliation
